# My Growth module rules
- Meeting integration mounts growth routes beneath the existing persistent student layout; confirmed reviewers get additive home/learning content and scoped appointment menus, without changing LMS roles. Legacy growth-home/list URLs redirect to existing pages. Why: demo navigation must preserve the same academy shell while server record scope remains authoritative.
- Time reports aggregate existing records read-only via one scoped RPC (education team all, appointed senior own current branch, employee self); manager-coaching minutes count only for the employee and the authoring store manager. Why: reports must not widen coaching access or alter learning records.
- Report exports call that RPC afresh, discard results after selection/user changes, preserve visibility flags and neutralize spreadsheet formulas. Why: stale cached rows must not bypass revocation or change report semantics.
- Report and team interface labels use the module translation bundle; export formatting stays Korean and source record names/text stay untouched. Why: language switching must not change export requirements or disclose source text to translation services.
- Team growth summaries come from one read-only scoped RPC (education team any branch, appointed senior current branch only); manager-coaching counts only for the authoring manager and staff detail links only where existing staff scope allows. Why: team overviews must not widen coaching or record access.
- Remaining module and growth-menu labels use `uiText.ts` `k()`/`kMap()` (Korean source text as key, read at render time); record names, titles and coaching text are never passed through it. Why: language switching must cover every screen without translating or sending source records.
- HQ education-team access to staff details and manager coaching is a single server-side toggle (default off, education team only, audited) checked inside `mygrowth_staff_record_scope`; HQ stays read-only for follow-ups. Why: opening must be reversible instantly without widening store-manager or trainer scope.
- External KPI ingestion enters only through the `mygrowth-kpi-ingest` function with per-vendor API keys stored as SHA-256 hashes; a service-only RPC validates rows, upserts by employee/month/metric and logs each batch. KPI tables have no client policies; reads go through reviewer-gated RPCs using the existing education/senior-branch/self scope. Why: vendor data must not widen record access or allow client writes.
