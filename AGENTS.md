# AGENTS.md

## Architecture rules

- PWA install metadata uses the same-origin `public/manifest.webmanifest` as its sole source; Vite must not emit a competing manifest. Preserve the installed app identity and start URL when changing icons. Why: cross-origin dynamic manifests resolve relative icons against the wrong host, and changing identity duplicates installed apps.

- Dashboard layout is route-level and persistent: `RoleLayoutRoute` (src/components/layouts/RoleLayoutRoute.tsx) wraps each role section in App.tsx and renders `DashboardLayout` + `<Outlet />`. Pages must NOT wrap themselves in `DashboardLayout` — return page content only. Why: per-page layouts remount the sidebar on every navigation.
- Pages needing a custom `<main>` class use `useContentClassName()` from DashboardLayout instead of the removed `contentClassName` prop. Why: pages no longer own the layout.
- `AppErrorBoundary` must not be keyed by `location.pathname` — a keyed boundary remounts the whole tree per navigation and defeats layout persistence.
- `RoleLayoutRoute` wraps its `<Outlet />` in its own `<Suspense fallback={<ContentSkeleton />}>`. Why: lazy page chunks otherwise suspend up to the app-wide Suspense and replace the sidebar with a full-screen skeleton.
- Route guards (`ProtectedRoute`/`AdminRoute`/`TeacherRoute`) only show the full skeleton while no authorized user is known. Why: background auth refreshes must not unmount the persistent layout.
- My Growth development and QA must run in a separate draft with verified isolated dependencies; fail closed if live database, storage, functions, jobs, or integrations remain reachable. Never alter production routes, roles, settings, backups, or learning data during development. Why: all existing roles must retain their current service until an explicitly approved integration release.
- Before any My Growth work in a draft, run `bash scripts/mygrowth-draft-isolation.sh apply` then `verify`; stop if verify reports any FAIL. Blocks are runtime-only and vanish on sandbox restart; edge function code must not use raw sockets (`Deno.connect*`). Why: kernel firewalls are unavailable, so draft isolation relies on proxy/hosts blocks, removed integration secrets, disabled auth mail hook and revoked pg_net/pg_cron grants.
- `/my-growth` access is decided only by the server function `is_mygrowth_reviewer()` over `mygrowth_reviewers` (service-role writes only, no client grants); errors fail closed and admin roles or browser settings never grant access. Why: the reviewer gate must not become an authorization bypass.
- My Growth record reads require both server-confirmed reviewer membership and ownership; the route gate must revalidate membership without retaining stale authorization. Why: hiding a screen does not protect direct data requests or revoked reviewers.
- My Growth appointments use service-only education authority and senior/branch registries, separate from LMS roles; RPCs derive tenant and branch from trusted registry plus current profile, and transfers invalidate appointments. Why: existing administrator roles, editable titles, and client-supplied branches must never widen appointment or branch access.
- Offline training and pending targets are created only through an atomic, idempotent RPC that validates current trainer assignment and staff scope; registration never writes LMS or completed growth records. Why: partial saves, retries and unconfirmed attendance must not alter learning totals.
- Attendance uses a separate outcome column and atomic scoped RPC with version conflict detection and immutable audit history; no LMS or growth-completion writes. Why: registration compatibility, concurrent edits, and attendance corrections must not corrupt learning records.
- Employee learning lists live only under the reviewer-gated My Growth routes and project own source records through a read-only RPC; attendance overrides linked training copies and canonical sources suppress duplicate events. Why: existing student screens stay unchanged and corrected attendance cannot leave stale completion copies visible.
- Field coaching stores notes in a one-to-one extension of the shared training session, creates both atomically through a scoped RPC, and uses the same targets/attendance audit; session_kind separates lists and employee projections. Why: attendance is not duplicated and coaching must never appear as education.

- Manager coaching is created only by the assigned store manager in their current branch; the shared session scope dispatches by session_kind and limits manager sessions to their author, without widening trainer/education scope. Notes, targets and attendance audit are atomic and employee projections are attendance-driven. Why: sensitive manager feedback must not leak to education roles or permit cross-kind attendance writes.
- Employee action plans live in a table with no client grants; only RPCs write/read them: the owner saves one plan per attended session target, and staff read others' plans only through `mygrowth_session_scope`. Why: plans must not widen field/manager coaching access or touch learning and attendance records.
- Followup assessments are append-only RPC-only audit rows with plan/assessor snapshots; writes require reviewer membership, current branch assignment, session scope and attended target, with locked plan/version and idempotent request checks. Why: corrections must preserve history without widening coaching scope or changing learning records.
- My Growth employee navigation and staff workspaces stay inside the reviewer-gated module and derive capabilities only from server-confirmed appointments; employee home, timeline and details reuse canonical owned projections and existing plan/followup RPCs. Why: client layouts must not grant LMS administrators new authority or duplicate sensitive records.
